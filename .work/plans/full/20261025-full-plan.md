## 1. Executive Summary

The product generates passwords and passphrases, and provides an AWS-compatible Secrets Manager for its own policy. It already runs in production; this plan does **not** build the product, it closes the gap between "works" and "safe to operate".

Six milestones, ~21 tasks. The sequence is deliberate: **M1 ships the already-verified hardening** (it is uncommitted and therefore undeployable today), then least privilege, correctness, restore safety, observability, and finally test depth. Nothing in M2–M6 requires a live schema migration; the store format is unchanged.

Top risks: the hardening is still uncommitted and undeployable (`R5`); the app still holds the instance-admin credential (`R7`); backups are plaintext-equivalent (`R10`); there is no CI (`U2`, `NFR7`).

## 2. Project Goals

| # | Outcome | Success metric |
|---|---|---|
| G1 | Existing clients never break | Contract suite green against the deployed revision before every release; zero client-visible failures in the post-deploy verification |
| G2 | Privileged operations are not reachable from the internet | Every `*ClientCredential` target returns 403 at the edge and `AccessDeniedException` on the public listener |
| G3 | A bad deploy is recoverable in minutes | `./bin/start.sh rollback` restores a healthy stack, drilled on prd |
| G4 | Secret material is not world-readable or backup-leaked | 0600 everywhere; off-host backups encrypted |
| G5 | Abuse is bounded at the edge and in the container | `limit_req`/`limit_conn` live; app capped at 8 concurrent runs |
| G6 | The operator can see degradation | Generate latency/refusal metrics and a generation-verifying health probe |

## 9. Architecture Overview

Five bounded contexts with an acyclic dependency direction: BC-GEN (Python generator), BC-WEB (Next.js surface), BC-SM (Secrets Manager), BC-OPS (control plane/CLI), BC-EDGE (host nginx). Full detail, diagram and fitness review: [foundation doc 04](../../plans/foundation/20261025-04-foundation-architecture.md).

```text
internet ─443─► nginx (TLS, deny-map, limit_req) ─► app :3000 ─► python3 (≤8 concurrent)
                                              └────► secrets :8080 (data plane)
                                          loopback :8081 (admin plane intranet only)
```

## 10. UX/UI Strategy

One screen, one primary action, never implying persistence. Personas, journeys, state obligations and accessibility targets: [`20261025-personas-v1.md`](../../plans/20261025-personas-v1.md). Accessibility is **unverified** until M6-T2; no WCAG claim may be made before then.

## 11. Data Strategy

Single AES-256-GCM encrypted JSON document (`schemaVersion: 1`) on a named volume — no SQL, no migrations (ADR 004). Generated passwords are never persisted. Retention: soft delete with a 7–30 day recovery window, purged on access. Any format change requires a migration runner (out of scope here).

## 12. Security Strategy

Threat model: [18 threats, 6 trust boundaries](../../standards/20261025-threat-model.md). Controls shipped 2026-10-25: edge XFF overwrite + rate limits, container resource ceilings, prd read-only rootfs, 0600 secret material, child-env allowlist, body caps, fail-closed limiter capacity. Open and scheduled here: least privilege (M2), backup custody (M4), health disclosure (M5).

## 13. Infrastructure Strategy

Single VPS, Docker Compose per environment, host nginx for TLS. Resource ceilings declared per service (`mem_limit`/`cpus`/`pids_limit`); app rootfs read-only in prd. Loopback-only publishing for app and secrets ports. No orchestration platform (NFR6).

## 14. Deployment Strategy

Today: `./bin/start.sh up|recreate|rebuild <env>` with a pre-build image snapshot. Target state after M1: **every release is a tagged commit with a recorded image digest**, deployed as backup → rebuild → recreate → install/reload nginx → verify → record. No CI yet (`U2`); M6-T3 introduces a minimal pipeline. Rollout is all-at-once (single host); the rollback path is the safety net, not blue/green.

## 15. Scalability Strategy

Held deliberately small: one writer, one volume. Bound is the store, not the app (R12, accepted). The app scales vertically to the container limits; generation concurrency is capped at 8. Revisit only if the deployment model changes; resolving it means replacing the store backend, not adding replicas.

## 16. Observability Strategy

Today: structured JSON logs with `requestId`, `/healthz`, `/readyz` (public payload reduced). Gaps: no metrics, no SLOs, health never exercises generation. Target: emit `generate.success`, `generate.refused{reason}`, `policy.source` counters and an SLO of p95 < 2 s / error rate < 1 % (M5). Ties to `.work/standards/OBSERVABILITY_SPEC.md`.

## 17. Testing Strategy

| Layer | Today | Target |
|---|---|---|
| Service contract | **40 tests** (`node --test`), green on `269b9c6` and the tree | keep as the compatibility gate |
| App unit | **22 tests** (`npm test`, zero deps) | extend to wordlist/separator paths (M3) |
| End-to-end smoke | **13 checks** incl. refusal paths | add degraded-readiness case (M6) |
| Type/lint | `tsc --noEmit && eslint` | unchanged |

## 18. Operational Strategy

Runbooks: `README.md` §9, `docs/production-deployment.md`. Incident classes: (a) generation unavailable, (b) secrets manager unavailable, (c) bad deploy, (d) credential compromised. Each maps to a verified path: (a) `/api/health` + logs, (b) degrade-and-serve defaults, (c) `rollback`, (d) `rotate-client-credential` then revoke. On-call is the single operator.
