# secrets-manager v1 wire contract — SPEC

Pins the **deployed** AWS-Secrets-Manager-compatible contract of `secrets-manager/` so that every later change is coverage-checked against it.

**Status:** Draft — 2026-10-25
**Needs:** owner sign-off on BC6 (`/readyz` payload reduction) and BC9 (public operation-list filtering), which are the two intentional behaviour changes in the uncommitted hardening diff.

---

## 1. Purpose

Two live clients depend on this service today: the password-generator app (static, read-only, prefix `password-generator/<env>/`) and an ACB client (prefix `client/acb/`). The service has **no automated tests** (`.work/plans/UNKNOWNS.md:8`, U1), so "the clients keep working" is currently an assertion, not a measurement.

This SPEC converts that assertion into numbered, testable rules. The suite built from §9 must pass **against unchanged code at commit `269b9c6`** before any remediation begins.

## 3. Scope

**In scope:** the HTTP surface, SigV4 authentication and authorization, the 17 operations, error taxonomy, the encrypted store's on-disk compatibility, and the health/info endpoints.

**Out of scope:** the app's `POST /api/generate` (separate SPEC), nginx edge configuration, `bin/start.sh` control verbs, and AWS SDK behavioural parity beyond the operations listed.

## 4. Domain language

| Term | Meaning |
|---|---|
| **Principal** | An authenticated caller resolved from an access key: either the instance admin or a client credential. Carries `accessKeyId`, `name`, `admin`, `allowedPrefixes`, and (working tree only) `readOnly`. |
| **Static client** | A principal defined by `SM_CLIENTS_JSON` in the environment. |
| **Managed client** | A principal persisted in the encrypted store, created via `CreateClientCredential`. |
| **Prefix scope** | `allowedPrefixes`: a client may only touch secrets whose name starts with one of its prefixes. |
| **Read-only** | Working tree only. Defaults to `false` for records that do not carry the field. |
| **AWSCURRENT / AWSPREVIOUS** | A secret version's stages; exactly one version holds `AWSCURRENT`. |
| **Soft delete** | `DeleteSecret` sets `DeletedDate`; `RestoreSecret` clears it; a soft-deleted secret is excluded from `ListSecrets` and reports `deletedSecrets`. |

### 5.2 Authentication rules

| ID | Rule | Evidence |
|---|---|---|

## 6. Data model and on-disk compatibility

| ID | Rule | Evidence |
|---|---|---|
| R23 | The store is a single encrypted JSON document holding `{secrets: [], clients: []}`; created with those two empty arrays when absent. | `store.mjs:191-197` |
| R24 | Secret **values** are encrypted with AES-256-GCM; names, ARNs, tags and dates are stored in clear. | `store.mjs:70`, `:643` |
| R25 | Each version's additional authenticated data is `<arn>\|<versionId>`, so a ciphertext cannot be moved between versions or secrets. | `store.mjs:681-691` |
| R26 | Exactly one version holds `AWSCURRENT`; a rotation demotes the previous current to `AWSPREVIOUS`. | `store.mjs:762-799` |
| R27 | Version IDs are UUIDs. | `store.mjs:796` |
| R28 | A soft-deleted secret keeps its ciphertext and version history; it is excluded from `ListSecrets` and counted in `deletedSecrets`. Reading it returns `InvalidRequestException` "You can't perform this operation on the secret because it was marked for deletion." — this matches AWS, which uses `InvalidRequestException` (not `ResourceNotFoundException`) while a secret sits in the recovery window. | `store.mjs:930-940`, `:1605-1610` |
| R33 | `ListClientCredentials` returns `{ClientCredentialList: [...]}` sorted by name; each entry is `{Name, AccessKeyId, Description, AllowedPrefixes, Source}` with `Source` in `static \| managed`. The working tree adds `ReadOnly`. | `store.mjs:348-356`, `:490-499` |
| R34 | `GetClientCredential` returns the credential record **including `SecretAccessKey`** and therefore requires admin; the list projection never includes secrets. | `store.mjs:505-515` |

### 5.5 Credential lifecycle and rotation (S5)

| ID | Rule | Evidence |
|---|---|---|
| R35 | `CreateClientCredential` returns the new `SecretAccessKey` once, plus `Name`, `AccessKeyId`, `Description`, `AllowedPrefixes`, `Source: "managed"`. Names are unique and must match `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`. | `store.mjs:533-608` |
| R36 | A managed credential authenticates exactly like a static one and is subject to the same prefix scoping. | `store.mjs:595-608`; test `R36` |
| R37 | **Two credentials may coexist for the same prefix.** This is what makes rotation outage-free: mint the successor, cut the client over, then revoke the predecessor. Revoking one credential must never invalidate another. | test `R37` |
| R38 | Static credentials (`SM_CLIENTS_JSON`) cannot be deleted through the API; the request fails with `InvalidRequestException` instructing an environment change. | `store.mjs:619-626` |
| R39 | The operator CLI (`cli.mjs`) targets the **loopback admin listener** for credential operations (`SM_ADMIN_ENDPOINT`, default `http://127.0.0.1:8081`). On a pre-hardening deployment it falls back to the public endpoint with a warning on stderr; an explicitly configured `SM_ADMIN_ENDPOINT` never falls back. | `cli.mjs` `callAdmin` |
| R40 | `rotate-client-credential <name>` mints `<name>-<suffix>` inheriting the predecessor's `AllowedPrefixes` and `Description`, and leaves the predecessor valid unless `--revoke-old` is passed. `revoke-client-credential <name>` completes the rotation. | `cli.mjs` |
| R29 | The master key comes from `SECRETS_MANAGER_MASTER_KEY` (source `env`) or, failing that, a `master.key` file in the data directory (source `file`); an unreadable/undecryptable store fails fast rather than serving empty data. | `store.mjs:122`, `:153-178`, `:259` |
| R30 | Managed client records load with `allowedPrefixes` defaulted to `[]` and `readOnly` defaulted to `false` when the field is absent — a pre-existing record must not become read-only by upgrade. | `store.mjs:106-110` (working tree) |
| R31 | Static and managed clients are distinguished in `GetClientCredential` output by `Source: "static" \| "managed"`. | `store.mjs:348-356` |

|---|---|---|

| `ResourceExistsException` | 400 | Secret already exists |
| `InvalidParameterException` | 400 | Bad parameter |
| `InvalidRequestException` | 400 | Malformed request / path / method |
| `AccessDeniedException` | 400 | Authenticated but not authorized |
| `MissingAuthenticationTokenException` | 400 | No credentials presented |
| `UnrecognizedClientException` | 400 | Unknown access key |
| `InvalidSignatureException` | 403 | Signature mismatch |
| `SerializationException` | 400 | Body is not valid JSON |
| `UnknownOperationException` | 400 | Unknown target / operation |
| `InternalServiceError` | 500 | Unhandled server fault, message always `"Internal error."` |

## 8. Backwards-compatibility invariants (the compat net)

These are the rules that protect the two live clients. Each is a test, not a promise.

| ID | Invariant | Why it can break |
|---|---|---|
| **BC1** | The password-generator's **static** credential still authenticates and still reads `password-generator/<env>/*`. | Any change to SigV4 canonicalization, static-client parsing, or prefix matching. |
| **BC2** | The ACB `client/acb/*` client still authenticates and reads/writes only within `client/acb/`. | Prefix-boundary bugs, e.g. treating `client/acb2/` as inside `client/acb/`. |
| **BC3** | Operation names, the `/` path, and the `x-amz-target` format are unchanged. | Renaming or re-scoping an operation. |
| **BC4** | Error `__type` strings and HTTP statuses are unchanged for the existing failure modes. | Error refactors. |
| **BC5** | `GET /healthz` keeps its exact field set and 200 status. | Monitors parse it. |
| **BC6** | `GET /readyz` keeps its **status code** semantics (200 ready / 503 not ready). Its payload may shrink only as a versioned, documented change. | Docker/compose healthchecks and external monitors. |
| **BC7** | Existing managed-client records remain usable after upgrade — `readOnly` defaults to `false`, so no existing client silently loses write access. | The new `readOnly` flag. |
| **BC8** | Existing ciphertexts remain decryptable: no change to the AAD format, the key derivation, or the store layout without a migration. | Encryption refactors. |
| **BC9** | The set of operations reachable **without a loopback admin listener** may shrink only by an explicit, documented decision. Removing the four `*ClientCredential` ops from the public listener is an **intended** change, not an accident, and must be recorded in an ADR plus a changelog entry. | The hardening diff. |
| **BC10** | Version/stage/soft-delete semantics are unchanged: `AWSCURRENT` uniqueness, `AWSPREVIOUS` demotion, `DeleteSecret` → restorable, `RestoreSecret` → visible again. | Store refactors. |

**Note on BC9:** the four credential operations are administrative, not data-plane. The likely live impact is on *credential minting*, not on client authentication — the ACB client's stored credential keeps working even when the operations that created it become loopback-only. This must be confirmed with the owner before the change ships (see §11).

## 9. Test plan

A new zero-dependency suite at `secrets-manager/test/` using `node:test` (matches the service's zero-npm-dependency design; no lockfile change, no supply-chain surface).

| Test ID | Covers | Shape |
|---|---|---|
| T-SIGV4 | R11–R17 | Replays a signed request against a temp store; asserts pass, then mutates one byte of the signature / date / body hash and asserts each specific error code. |
| T-AUTHZ | R19–R22 | Static client with prefix `client/acb/`; asserts allowed read, denied read outside prefix, and boundary case `client/acb2/x` denied. |
| T-SURFACE | R1–R10, BC3, BC5 | `GET /healthz`, `/readyz`, `/`, `/info`; asserts field sets, status codes, sorted operation list and its exact 17 members. |
| T-ERRORS | R7, R8, R32, BC4 | Non-JSON body, non-object body, unknown target, unknown operation, unknown path; asserts `__type` and status. |
| T-STORE | R23–R31, BC8, BC10 | Create → put → get → rotate (AWSPREVIOUS) → soft delete → restore → list; asserts ciphertext round-trip and count fields. |
| T-MIGRATE | R30, BC7 | Writes a store document whose client records lack `readOnly`; asserts it loads and the client can still write. |

**Gate:** every test above must pass against the **unchanged** `269b9c6` code (using `git stash`/worktree isolation) before any source file is modified. A rule that cannot be tested as written is a defect in this SPEC: amend the SPEC, do not weaken the test.

**Run command (host, zero deps):** `node --test secrets-manager/test/`
This is a `node:test` invocation with no install and no build step, so it does not violate the compose-only rule for app builds; it is documented here as the sanctioned exception (`.cursorrules` §Docker, "Only if `DOCS_TECH_STACK.md` documents it").

## 10. Decisions needed

1. **BC6** — approve reducing the public `/readyz` payload to `{status, ok, version}`, keeping HTTP status semantics. Store internals move to the loopback listener. (Addresses feedback F-06.)
2. **BC9** — approve that the four `*ClientCredential` operations become loopback-admin-only on the public listener, and that this is recorded in an ADR + changelog before deploy. (Addresses feedback F-04.)

## 11. Open questions

1. **Does ACB mint credentials at runtime, or only consume one?** If it calls `CreateClientCredential`/`GetClientCredential` from outside the host, BC9 is a breaking change for it and needs a compatibility window (`U4`).
2. **Is the generator's static client flag `readOnly: true`?** If yes, BC7 is the rule that matters most; if no, the field is inert today (`U5`).
3. **Which monitor consumes `/readyz`?** Compose healthcheck, an external probe, or both — determines whether BC6 is observable externally (`U6`).
